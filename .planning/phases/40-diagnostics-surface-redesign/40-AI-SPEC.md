## 1. System Classification

**System Type:** Hybrid (Developer Diagnostics Console + Tooling Automation)

**Description:**
`nexagent` is a local developer console that surfaces model runtime state, diagnostic details, tool traces, and command outcomes for operator control. The phase should keep default output compact and operator-readable while preserving explicit access to deeper detail for debugging.

**Critical Failure Modes:**
1. Diagnostics summaries become misleading or stale (false status about provider/tool health).
2. Compact mode hides operationally critical failures that need escalation.
3. Detail-mode transitions break trust by returning inconsistent structure or truncated context.

## 2. Framework Decision

**Selected Framework:** OpenAI-compatible Provider SDK via `openai` Node client (`openai` package)

**Version:** `openai@^5.x`

**Rationale:**
This phase is currently output-focused and already bounded by a TypeScript CLI runtime. A lightweight provider client keeps dependencies minimal and avoids framework lock-in while still supporting consistent structured outputs, tool call interfaces, and future traceability hooks.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|---|---|
| LangChain | Added abstraction overhead for a phase whose core work is UX/diagnostic behavior, not complex orchestration |
| LangGraph | Too heavy for this phase and unnecessary state-machine runtime complexity |
| CrewAI | Python-only execution model does not fit this TypeScript-first codebase |

**Vendor Lock-In Accepted:** Partial — runtime uses provider-agnostic interfaces where possible, but `openai` SDK is currently the practical adapter default.

### Installation

### Core Imports

```ts

```

### Entry Point Pattern

```ts
import OpenAI from 'openai';
import { z } from 'zod';

const client = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

const statusSchema = z.object({
  summary: z.string(),
  healthState: z.enum(['ok', 'warning', 'error']),
  blockers: z.array(z.string()),
  details: z.array(
    z.object({
      area: z.string(),
      finding: z.string(),
      severity: z.enum(['low', 'medium', 'high'])
    })
  )
});

export async function summarizeDiagnostic(input: { prompt: string }) {
  const response = await client.responses.parse({
    model: 'gpt-4o',
    input: input.prompt,
    text: {
      format: {
        type: 'json_schema',
        name: 'DiagnosticSummary',
        schema: statusSchema
      }
    }
  });

  return statusSchema.parse(response.output_text ? JSON.parse(response.output_text) : null);
}
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---|---|---|
| `response.parse` / schema checks | Validates structured output before rendering | Every command-summary write path |
| `provider health block` | Encodes runtime subsystem status | `/status` default and verbose output branches |
| `detail flag` | Expands compact output with audit-safe context | User requests with `--verbose` or `/command --detail` patterns |
| `transcript boundary event` | Marks command/response seams for copyability | Timeline and scrollback rendering |
| `guardrail check` | Pre-output gate for unsafe or ambiguous results | Before approving state transitions or tool output |

### Common Pitfalls

1. Missing schema enforcement leads to non-deterministic blocks and broken rendering.
2. Trusting provider responses without severity mapping causes ambiguous UX state.
3. Overusing verbose output by default makes operator triage slower and increases leak risk.
4. Forgetting to redact secrets before transcript persistence creates security debt.
5. No correlation IDs blocks cross-file trace joins during incidents.

### Recommended Project Structure

```
src/
  cli.ts                # Command dispatch + UI boundary
  diagnostics/
    status.ts           # Compact + detail formatting helpers
    provider.ts         # Health/probe adapters
    transcript.ts       # Boundary markers + redaction helpers
  llm/
    schema.ts           # Validation schemas (zod)
    outputs.ts          # Structured output contracts
```

## 4. Implementation Guidance

**Model Configuration:**
Use `gpt-4o` for higher semantic compression in status summaries and tool classification; set temperature to `0.2` for deterministic diagnostics; cap tokens low for compact mode and allow larger limits only for detail mode.

**Core Pattern:**
Build diagnostics as pure functions that return contract-shaped objects, then render compact strings in default mode. Keep AI involvement optional and strictly behind validated schema conversion.

**Tool Use:**
Prefer deterministic file-state tools for core truth (`status`, `memory`, `provider`, `tools`). AI should assist only on natural-language summarization, and only after strict schema validation of source facts.

**State Management:**
Store only non-sensitive telemetry in a rotating in-memory cache and append redacted command result blocks to transcript storage with IDs. Avoid persisting raw credentials or raw tool responses with secrets.

**Context Window Strategy:**
Keep compact prompts under one diagnostic turn; pass only relevant facts (health, blockers, action items) and exclude raw payloads unless `verbose` is true.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

Use schema-level validation and fail-closed behavior even when framework is TypeScript-first; treat the schema contract as the canonical API.

```python
from pydantic import BaseModel, Field, ValidationError, TypeAdapter
from typing import Literal, List

class Finding(BaseModel):
    area: str = Field(min_length=1)
    finding: str = Field(min_length=3)
    severity: Literal["low", "medium", "high"]

class DiagnosticSummary(BaseModel):
    summary: str = Field(min_length=5, max_length=240)
    health_state: Literal["ok", "warning", "error"]
    blockers: List[str] = []
    details: List[Finding] = []
```

Retry strategy:
- If parse fails: 1 retry with an explicit "return strict JSON schema only" prompt.
- If parse fails twice: mark result as `warning`, include parse error metadata, and route through safe fallback summarizer.
- Always log schema failure type and raw provider request ID.

### Async-First Design

Use async provider calls with bounded concurrency; avoid `await` in synchronous rendering loops that can block terminal repaint.

### Prompt Engineering Discipline

Keep system-level instructions separate from user prompt; pass domain constraints explicitly (`"Do not reveal secrets"`). Set token caps for compact mode and reject over-long tool summaries before render.

### Context Window Management

Apply deterministic pruning:
- keep full state blocks only for verbose mode;
- compact mode keeps 1-3 top blockers + status line.

### Cost and Latency Budget

Target median summary path under 300 ms with no network calls for cached command states. For AI-assisted summaries, budget:
- compact path: < 800 ms
- verbose path: < 2000 ms
Use cheaper model for frequent status refresh loops and keep heavy prompts behind explicit user action.

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail or 1-5) | Measurement Approach | Priority |
|---|---|---|---|
| Status truthfulness | PASS if compact output matches source state and failure flags; FAIL if any mismatch or stale state is shown | Code | High |
| Traceability integrity | PASS if every result block has stable command ID + severity label; FAIL if blocks cannot be linked | Code + Human | High |
| Progressive disclosure quality | PASS at 1=confusing 5=clear (domain expert can find cause in ≤2 interactions); FAIL if critical info hidden in compact mode | Human | Medium |
| Structured-output reliability | PASS when schema validation success rate ≥ 99% on sampled requests; FAIL when invalid output is rendered directly | Code + Human | High |
| Safety guardrail behavior | PASS when ambiguous/hazardous summaries are escalated; FAIL when they are treated as safe | Code + LLM judge | Critical |

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|---|---|---|
| Stale status blocker | Rendered status mismatch with probe age or cache TTL | Block unsafe action, show explicit stale warning and refresh command |
| Validation fail hard-stop | Schema parse fails twice | Escalate to safe fallback text and skip AI-render path |
| Secret leak check | Sensitive pattern detected in response | Redact tokenized fields before transcript write |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|---|---|---|
| schema_parse_failure_rate | Daily sample of diagnostics calls | Add examples to prompt/guardrail corpus and retrain failure handling |
| stale-status rate | Monthly incident review on command blocks | Adjust TTL strategy and health probe cadence |
| rework_loop_count | Weekly postmortem sampling of rejected runs | Improve compact/verbose balance and copy quality |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (fallback to Langfuse if already in-house)

**Key Metrics to Track:**
- median/status summary latency
- schema validation pass rate
- detail-mode conversion success rate
- stale-state incidents
- redaction violations

**Alert Thresholds:**
- schema parse fail rate > 2% over 15m
- stale-state incident > 3/hour
- redaction violation > 0
- summary latency p95 > 2s

**Smart Sampling Strategy:**
- sample all failures and warnings
- sample 10% of green/success responses for trend
- oversample cases with retries, escalations, and abrupt detail-mode switches
