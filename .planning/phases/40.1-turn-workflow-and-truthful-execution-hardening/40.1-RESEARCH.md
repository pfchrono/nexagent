## User Constraints (from CONTEXT.md)

### Locked Decisions
- Phase 40.1 hardens turn execution truthfulness and operator controls in the runtime:
- explicit completion truth requires state-level confirmation
- long-run operations report blockers and verification state honestly
- status visibility becomes predictable and compact-first
- cancel/approval control paths become unambiguous

### Turn flow semantics
- **D-01:** Continue behavior stays active execution loop until done or blocked; `continue` does not mean one extra shot.
- **D-02:** `finish` during active execution performs graceful soft-stop and surfaces completed/in-progress/blocker details.
- **D-03:** Mid-loop block (approval, cancel, loop cap) stops immediately and returns blocker context.

### Completion signal and validation
- **D-04:** Completion is state-based only: provider done, no pending action, no queued work.
- **D-05:** Missing completion signal blocks `finish`; state marked unverified and shown as not done.

### Progress and truth labels
- **D-06:** Keep runtime action model unchanged; expose derived labels for UI/status only.
- **D-07:** `running` = active model/tool execution; `pending` = operator-gated/waiting.
- **D-08:** `finished` requires explicit execution success and no pending work.
- **D-09:** First transition signal appears in TUI footer statusline.

### Cancel and approval behavior
- **D-10:** `/cancel` triggers immediate cancel attempt and explicit canceled+blocker entry.
- **D-11:** Approval needed path shows blocked state and explicit "awaiting approval" summary.
- **D-12:** `finish` while approval pending pauses and keeps request alive.
- **D-13:** Missing `/approval` after clear prompt repeats once and waits.

### Failure and stop conditions
- **D-14:** Empty provider exit with status 0 counts as failure-to-respond.
- **D-15:** Empty responses are unverified until explicit completion summary exists.
- **D-16:** Provider/auth/model/transport failures map to blocked external dependency with action summary.

### Long-turn visibility defaults
- **D-17:** Compact /status defaults minimal fields: state, phase, objective.
- **D-18:** Long-turn trace defaults compact; full detail shown on explicit request.
- **D-19:** Compact /status includes blocker reason inline.
- **D-20:** Transcript prioritizes blockers/errors first, then state transitions.

### Claude's Discretion
- No additional specific style constraints beyond compact-truthful defaults.

### Deferred Ideas (OUT OF SCOPE)
- Agent loop policy details for cap-failure outcome left to implementation pass.

## Summary

Phase 40.1 is state-first hardening, not command expansion. Current runtime already has the control points needed for truthful execution (`runPromptCommand`, provider loop, approval/cancel controls, derived status summaries), so phase risk is behavioral correctness and observability completeness, not adding infrastructure. [VERIFIED: src/cli.ts][VERIFIED: src/provider.ts][VERIFIED: src/runtime/session.ts]

Primary recommendation: enforce a single completion criterion in session state (`provider done + no pending action + no queued work`) and keep `/finish`/operator gates as state-preserving controls, then make every long-turn output path derive from that criterion. [VERIFIED: src/runtime/session.ts][VERIFIED: 40.1-CONTEXT.md]

Secondary recommendation: keep internal status enum stable, add derived labels and transcript entries for blocked, failed, and unverified states only; avoid adding a new runtime enum branch unless migration and command tests explicitly require it. [VERIFIED: src/runtime/session.ts][ASSUMED]

### Pattern 1: State-derived truth labels
**What:** keep minimal raw state in `session`, derive operator-facing labels (`running/pending/blocked/finished`) in presentation layer only. [VERIFIED: src/runtime/session.ts][VERIFIED: 40.1-CONTEXT.md]

```ts
// Derived label example from current design intent
type VisibilityState = "running" | "pending" | "blocked" | "finished" | "error"
function deriveLabel(session: {actionStatus: string; pendingApproval: boolean; cancelRequested: boolean; error?: unknown}) : VisibilityState {
  if (session.cancelRequested) return "blocked"
  if (session.pendingApproval) return "pending"
  if (session.actionStatus === "error") return "error"
  return session.actionStatus === "running" ? "running" : "finished"
}
```

### Anti-Patterns to Avoid
- **Output-based completion detection:** claiming "done" from text alone and skipping state checks. This violates explicit completion contracts in context decisions. [VERIFIED: 40.1-CONTEXT.md]
- **Implicit cancellation clearing:** clearing session blockers before explicit terminal state. Existing behavior expects blocker visibility in status/transcript. [VERIFIED: src/cli.ts]
- **Mixed state writes from UI and runtime without command guardrails:** risks inconsistent recovery after interruption. [VERIFIED: src/cli.ts][VERIFIED: src/provider.ts][VERIFIED: src/runtime/session.ts]

## Common Pitfalls

### Pitfall 1: Finish command interpreted as "always finish now"
**What goes wrong:** Planner sees finish as success even if action remains pending/approval-gated.  
**Why it happens:** `finish` is currently a control command, not an engine state replacement.  
**Avoid:** Keep `finish` behavior as graceful soft-stop and require explicit completion signal for done state. [VERIFIED: 40.1-CONTEXT.md][VERIFIED: src/cli.ts]

### Pitfall 2: Completion shown as true with empty provider output
**What goes wrong:** Exit code 0 with empty output is currently treated as provider failure to respond.  
**Why it happens:** Existing failure policy already maps this to error state.  
**Avoid:** Preserve existing empty-output error semantics while improving error visibility in trace/status. [VERIFIED: src/provider.ts]

### Pitfall 3: Approval deadlock on plain prompts
**What goes wrong:** Operator submits normal prompt while pending approval and receives blocked state with no path.  
**Why it happens:** Guard is currently command-gated.  
**Avoid:** Preserve required `/approval` flow and keep pending approval state explicit in compact status. [VERIFIED: src/provider.ts][VERIFIED: src/cli.ts]

### Pitfall 4: Lost continuity on cancel
**What goes wrong:** Cancel flag set but no explicit recovery summary for next continue cycle.  
**Why it happens:** Incomplete state handoff between provider loop and status rendering.  
**Avoid:** Ensure recovery section explicitly shows cancel/cancelled and allows explicit operator restart path. [VERIFIED: src/cli.ts][VERIFIED: 40.1-CONTEXT.md]

### Pitfall 5: Verbosity ambiguity during long turns
**What goes wrong:** Trace floods operator; blocker/error context buried below routine lines.  
**Why it happens:** Long-turn default not compact-first.  
**Avoid:** Preserve compact-first status and verbose-only expansion paths. [VERIFIED: src/cli.ts]
