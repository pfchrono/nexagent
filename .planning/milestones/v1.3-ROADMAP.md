# Roadmap: nexagent v1.3

Source: promoted from `.planning/NEXT-MILESTONE.md`.

## Overview

`v1.3` turns `nexagent` from working writable harness into more trustworthy daily-driver harness with stronger live-turn control, better provider parity, and tighter operator ergonomics.

## Phases

- [x] **Phase 30: Dogfood and rough-edge intake** - Gather real operator pain, compare against donor patterns, and lock first `v1.3` implementation direction.
- [x] **Phase 31: Live turn interruption and control hardening** - Restore dependable live turn behavior first, then strengthen cancel/approval/control states.
- [x] **Phase 32: Stronger steer semantics** - Make steer timing and operator feedback less ambiguous.
- [x] **Phase 33: Provider parity and transport truth** - Reduce transport-specific surprises and show honest capability truth.
- [x] **Phase 34: Internal tool surface expansion** - Add best-next bounded coding tools under one policy layer.
- [x] **Phase 35: Memory quality and policy refinement** - Improve save/retrieval usefulness while keeping lineage bounded and inspectable.
- [x] **Phase 36: TUI and operator UX polish** - Rebuild TTY around workspace-first layout, better composer/statusline, and thinner runtime/UI boundaries.

## Phase Details

### Phase 30: Dogfood and rough-edge intake
**Goal**: turn current TTY pain into concrete `v1.3` execution order.
**Depends on**: Nothing
**Success Criteria** (what must be TRUE):
  1. Real operator pain is captured in actionable findings.
  2. Donor runtime/TUI comparisons shape first implementation direction.
  3. Next code slice is clear enough to start without more blind exploration.
**Plans**: `30-01`

### Phase 31: Live turn interruption and control hardening
**Goal**: restore dependable live turn behavior and strengthen operator control state around active work.
**Depends on**: Phase 30
**Success Criteria** (what must be TRUE):
  1. Primary live provider path fails clearly or succeeds in bounded time.
  2. Cancel/approval/control state is more explicit and inspectable.
  3. Live turn path is healthy enough to resume meaningful control-path dogfood.
**Plans**: `31-01`

### Phase 32: Stronger steer semantics
**Goal**: make steer timing, persistence, and feedback less ambiguous.
**Depends on**: Phase 31
**Success Criteria** (what must be TRUE):
  1. Steer state is visible as queued/applied/deferred/rejected.
  2. Operator can tell when steer changed active work.
  3. Runtime surfaces preserve enough steer history to explain behavior.
**Plans**: `32-01`

### Phase 33: Provider parity and transport truth
**Goal**: reduce biggest behavior gaps across supported transports and expose honest capability truth.
**Depends on**: Phase 32
**Success Criteria** (what must be TRUE):
  1. Transport-specific capability gaps are visible in runtime surfaces.
  2. Provider progress/errors feed shared runtime truth instead of adapter-specific text only.
  3. Fewer operator surprises remain across `cli-exec`, `http-responses`, and `codex-http`.
**Plans**: `33-01`

### Phase 34: Internal tool surface expansion
**Goal**: add next high-value bounded coding tools without breaking policy coherence.
**Depends on**: Phase 33
**Success Criteria** (what must be TRUE):
  1. New tool additions serve real coding/operator needs from dogfood.
  2. Shared policy layer stays single source of truth.
  3. Tool visibility remains inspectable from runtime surfaces.
**Plans**: `34-01`

### Phase 35: Memory quality and policy refinement
**Goal**: improve usefulness of what gets saved and retrieved without making memory noisy or unbounded.
**Depends on**: Phase 34
**Success Criteria** (what must be TRUE):
  1. Retrieval quality improves for real operator tasks.
  2. Save/checkpoint behavior remains bounded and visible.
  3. Read/write lineage still explains why memory influenced a turn.
**Plans**: `35-01`

### Phase 36: TUI and operator UX polish
**Goal**: rebuild TTY into workspace-first operator surface over shared runtime truth.
**Depends on**: Phase 35
**Success Criteria** (what must be TRUE):
  1. Main TTY feels like workspace, not dashboard.
  2. Composer, statusline, tool traces, and autocomplete feel intentional.
  3. TUI stays thin over runtime state and supports reduced-clutter focus mode.
**Plans**: `36-01`
