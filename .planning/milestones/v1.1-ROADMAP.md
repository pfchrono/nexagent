# Roadmap: nexagent v1.1

Source: promoted from `.planning/NEXT-MILESTONE.md`.

## Overview

`v1.1` turns truthful baseline surfaces into practical harness behavior by importing scoped subsystems from local donor harnesses in `~/code/`: system prompt foundation, Codex OAuth/provider flows, richer commands, stronger TUI ergonomics, tool safety, git freshness, and deeper Archivist integration.

## Phases

- [x] **Phase 10: System prompt foundation** - Build working modular system prompt and layered prompt assembly for runtime sessions.
- [x] **Phase 11: Codex auth and provider activation** - Add `/login`, `/codex`, and OAuth-backed provider activation.
- [x] **Phase 12: Codex adapter and provider transport upgrade** - Integrate Codex API adapter and explicit auth/transport states.
- [x] **Phase 12.1: Complete transport parity and durable auth sessioning** - Finish HTTP adapter, broader provider parity, persisted auth/session state, and transport control commands.
- [x] **Phase 13: Command catalog expansion and statusline** - Import practical free-code command behaviors and statusline affordances.
- [x] **Phase 14: Hermes-style input ergonomics and TUI upgrades** - Add command/path autocomplete and stronger TUI progress ergonomics.
- [x] **Phase 14.1: Unique spinner emblem and progress chrome** - Create a nexagent-specific animated spinner/emblem blending Hermes-style progress discipline with free-code verb energy.
- [x] **Phase 15: Tool safety, git freshness, and shell policy** - Add shell guardrails, git freshness checks, and safer tool policy.
- [x] **Phase 15.1: Context compaction and compression control** - Add auto/manual compaction, threshold controls, queued-message handling, and compact state preservation.
- [x] **Phase 15.2: Internal tool registry and coding tool loop** - Add true model-callable local tools and runtime tool execution loop for repo work.
- [x] **Phase 16: Archivist runtime integration** - Integrate free-code Archivist runtime modules with explicit influence visibility.

## Phase Details

### Phase 10: System prompt foundation
**Goal**: Build a real working system prompt and layered prompt assembly for runtime sessions.
**Depends on**: Nothing
**Success Criteria** (what must be TRUE):
  1. Runtime has explicit system prompt sections grounded in implemented behavior.
  2. Prompt assembly stays modular and cache-stable.
  3. Repo-local instructions, tool guidance, safety rules, and truth boundaries are preserved.
**Plans**: `10-01`

### Phase 11: Codex auth and provider activation
**Goal**: Add `/login`, `/codex`, and OAuth-backed Codex provider activation.
**Depends on**: Phase 10
**Success Criteria** (what must be TRUE):
  1. Operator can authenticate Codex explicitly.
  2. Provider activation flows through shared runtime state.
  3. Auth state is visible and failures are explicit.
**Plans**: `11-01`

### Phase 12: Codex adapter and provider transport upgrade
**Goal**: Integrate Codex API adapter and strengthen auth-backed provider transport.
**Depends on**: Phase 11
**Success Criteria** (what must be TRUE):
  1. Codex adapter is integrated as runtime transport module.
  2. Auth/session-backed transport states are explicit.
  3. Provider transport truth remains inspectable across interfaces.
**Plans**: `12-01`

### Phase 13: Command catalog expansion and statusline
**Goal**: Import practical free-code command behaviors and statusline affordances.
**Depends on**: Phase 12.1
**Success Criteria** (what must be TRUE):
  1. Imported commands remain explicit and inspectable.
  2. Statusline reflects real runtime state.
  3. Compatibility wording is not mistaken for broader command parity.
**Plans**: `14-01`

### Phase 12.1: Complete transport parity and durable auth sessioning
**Goal**: finish Codex transport work that Phase 12 intentionally left out so runtime can support real adapter parity instead of CLI-backed truth only.
**Depends on**: Phase 12
**Success Criteria** (what must be TRUE):
  1. Full HTTP Codex API adapter exists alongside current CLI-exec adapter.
  2. Multi-provider transport parity goes beyond current Codex-backed path.
  3. Auth/session state can persist durably instead of per-process probe only.
  4. Command surface can control and inspect transport choice beyond passive visibility.
**Plans**: `12.1-01`

### Phase 14: Hermes-style input ergonomics and TUI upgrades
**Goal**: Add command/path autocomplete and stronger TUI input/progress ergonomics.
**Depends on**: Phase 13
**Success Criteria** (what must be TRUE):
  1. Command autocomplete works.
  2. File/directory autocomplete works from session cwd.
  3. TUI progress and token/status displays improve without forking runtime state.
**Plans**: `14.1-01`

### Phase 14.1: Unique spinner emblem and progress chrome
**Goal**: Create a unique `nexagent` spinner/emblem and progress line instead of copying donor TUI chrome.
**Depends on**: Phase 14
**Success Criteria** (what must be TRUE):
  1. Spinner/emblem visual is recognizably `nexagent`, not donor-identical.
  2. Hermes-style progress discipline and free-code verb richness both influence final chrome.
  3. Emblem, verb, and progress text derive from shared runtime state.
  4. Narrow-terminal fallback remains readable and stable.
**Plans**: `15-01`

### Phase 15: Tool safety, git freshness, and shell policy
**Goal**: Add shell guardrails, git freshness checks, and safer tool policy.
**Depends on**: Phase 14.1
**Success Criteria** (what must be TRUE):
  1. Important system paths are protected by visible policy.
  2. Repo inspection can surface branch freshness vs remote head.
  3. Tool safety remains explicit and inspectable.
**Plans**: `15.1-01`

### Phase 15.1: Context compaction and compression control
**Goal**: Add visible auto/manual context compaction with threshold control, compact state preservation, and queued-message behavior.
**Depends on**: Phase 14.1
**Success Criteria** (what must be TRUE):
  1. Runtime supports both auto-compaction and manual `/compact`.
  2. Threshold defaults use percent-of-context-window with visible remaining-token display.
  3. Compact payload preserves compact runtime state, active modes/skills, and queued next user message.
  4. Runtime distinguishes normal-turn steering from compact-turn queue/steer restrictions.
**Plans**: `15.2-01`

### Phase 15.2: Internal tool registry and coding tool loop
**Goal**: Replace slash-command-only local tooling as primary mechanism with true internal tools the model can call during coding turns.
**Depends on**: Phase 15.1
**Success Criteria** (what must be TRUE):
  1. Runtime has internal tool registry with schemas and handlers.
  2. Model can call repo-local read/search/list tools during provider loop.
  3. Internal tools reuse repo-local safety policy instead of bypassing it.
  4. Ripgrep-backed file/content search is available to internal tool flow when installed.
  5. Optional slash wrappers, if kept, call same internal handlers rather than duplicate logic.
**Plans**: `16-01`

### Phase 16: Archivist runtime integration
**Goal**: Integrate free-code Archivist runtime modules with explicit influence visibility.
**Depends on**: Phase 15.2
**Success Criteria** (what must be TRUE):
  1. Archivist runtime modules are integrated, not only boundary stubs.
  2. Retrieval influence is visible across interfaces.
  3. Memory policy remains bounded and explicit.
**Plans**: TBD
