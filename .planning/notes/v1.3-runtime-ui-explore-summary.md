## Topic

How `nexagent` should evolve from current working harness into better operator console with:
- workspace-first TTY
- thinner TUI over runtime
- clearer turn/control truth
- safer `src/cli.ts` breakup path

## Main conclusions

### 1. Core problem not visual first

Current worst issue not only styling.

Root issue:
- runtime truth too coarse
- TUI holds local transcript/activity strings
- provider/tool/control flow not represented as typed event history

Meaning:
- repainting current dashboard first would be wrong order
- first useful structural step = shared event model

### 2. Headless runtime should become canonical truth

Best donor rule held up:
- headless runtime owns turn/tool/control state
- TTY renders it

Implication:
- build `runtime/agent.ts` or equivalent turn runner
- let `provider.ts` stay transport-focused
- keep slash commands and TTY shell outside agent core

### 3. Small typed event model needed before bigger TTY redesign

Recommended minimum events:
- prompt accepted
- provider turn started
- provider turn failed
- assistant output updated
- assistant output completed
- tool requested
- tool completed
- tool failed
- approval requested
- approval resolved
- steer queued
- steer applied
- cancel requested
- cancel applied
- compact started
- compact completed

This enough for:
- workspace transcript
- grouped tool traces
- clearer statusline truth
- later interrupt/control work

### 4. Workspace-first TTY should replace dashboard-first TTY

Persistent default surface should be:
- compact statusline
- current turn/workspace
- transcript
- grouped tool trace area
- composer

Diagnostics should move behind:
- `/status`
- `/provider`
- `/tools`
- `/memory`
- maybe `/config`

### 5. `src/cli.ts` breakup should be smallest safe split, not rewrite

Best first split:

```text
src/
  runtime/
    agent.ts
    events.ts
  tui/
    renderer.ts
    input.ts
    config.ts
```

Keep in `cli.ts`:
- headless entry
- slash command routing
- TTY boot wiring

Do not split everything at once.

### 6. Tool traces should be first-class workspace surface

Best default:
- grouped tool display

Each trace should show:
- tool name
- short argument summary
- result state
- risk label if guarded
- duration when available

Not needed by default:
- giant raw output
- always-visible diagnostics panels

### 7. Plain fallback input mode should exist

Raw-mode TTY quirks already surfaced.

Need:
- plain fallback input mode
- maybe richer bordered mode later

Order:
- plain first
- styled mode after runtime/event cleanup

## Recommended `v1.3` order refinement

1. Dogfood intake
- keep collecting pain
- classify by transport / event model / TTY layout / control semantics

2. Event model foundation
- add runtime event log
- wire provider/tool/control boundaries into it

3. Control hardening
- cancel/steer/approval states emit explicit events

4. Provider parity
- show capability truth from same runtime model

5. TTY structural split
- extract renderer/input/config

6. Workspace-first redesign
- grouped tool traces
- compact statusline
- diagnostics on demand

## Non-decisions still open

- exact event payload schema
- whether assistant text should stream as deltas or replace-by-item model first
- exact statusline field order and truncation rules
- whether tool traces default to grouped or minimal on very narrow terminals

## Recommended next code move after dogfood

Smallest high-leverage code step:
- add typed runtime event log in shared session/runtime layer
- emit events from provider/tool/control boundaries
- keep current TTY alive, but make it render event log before more layout polish

This likely unlocks most `v1.3` work with least churn.
